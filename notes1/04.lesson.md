# PersonalClaw 开发经验教训

> 记录开发过程中遇到的问题和错误，避免重复。

---

## M1 开发中的错误

### 1. 违反"测试先行"原则（最严重）
- **错误**：先写功能代码，再写测试
- **正确做法**：先写失败的测试，再写代码让测试通过
- **违反**：宪法第2条"测试先行铁律 - 不可协商"

### 2. JSON vs YAML 混淆
- **错误**：一开始写了 `plugin.json` 而不是 `plugin.yml`
- **原因**：没有仔细阅读用户关于配置格式的明确要求
- **教训**：开始编码前仔细阅读需求文档

### 3. 未使用的导入
- **错误**：留下了 `encoding/json`、`bytes`、`context`、`errors` 等未使用的导入
- **原因**：代码重构后没有清理
- **教训**：每次修改后删除未使用的导入

### 4. 接口类型错误
- **错误**：`cmd *execCmd` 应该是 `cmd execCmd`（接口类型）
- **原因**：对 Go 接口类型理解错误

### 5. 测试中 slice 比较
- **错误**：直接比较 `[]string`，Go 中切片不可比较
- **原因**：切片类型的等值比较需要特殊处理

### 6. expandPath 不完整
- **错误**：函数没有处理单纯 `~` 的情况
- **原因**：边界条件考虑不全面

### 7. MarshalYAML 无限递归
- **错误**：`return c, nil` 导致无限递归
- **原因**：没有理解 yaml.Marshaler 接口的正确实现方式

### 8. mock 管道关闭问题
- **错误**：`defer cmd.Close()` 和 `defer proto.Close()` 两次关闭管道
- **原因**：对资源管理理解不足
- **教训**：只由协议 Close() 负责关闭所有资源

### 9. readResponses goroutine 错误处理
- **错误**：goroutine 在管道关闭后仍然尝试读取
- **原因**：没有正确处理 goroutine 退出
- **解决方案**：忽略"read/write on closed pipe"错误

### 10. 违反"拒绝 Mocks"原则
- **错误**：大量使用 mock 测试
- **原因**：宪法第2.4条要求优先编写 integration test
- **教训**：使用真实依赖进行集成测试

### 11. 单例 Logger 空指针解引用
- **错误**：在测试中调用 `logger.Get().Info()` 导致空指针解引用
- **原因**：logger 是单例，测试中未初始化就使用
- **解决方案**：在调用 logger 前检查是否为 nil，或使用 nil 检查模式 `if l := logger.Get(); l != nil { l.Info(...) }`
- **代码位置**：internal/agent/manager.go:102

### 12. 过度封装第三方库
- **错误**：为 `github.com/lixianmin/logo` 库创建了复杂的 wrapper 包，而不是直接使用
- **原因**：没有理解用户的意图是直接使用 logo 库
- **解决方案**：简化 logger 包，直接包装 `logo.NewLogger()`，暴露简单的 Init/Get/Close API
- **教训**：对于成熟的第三方库，直接使用比过度封装更好

### 13. 再次违反"测试先行"原则（重构场景）
- **错误**：在重构 logger.go 时直接修改代码，先确保测试能够编译通过
- **正确做法**：即使是重构，也应该先写测试或确保现有测试能运行，然后再修改代码
- **违反**：宪法第2.3条"在unit test编码完成之前, 不允许写任何功能代码"
- **代码位置**：internal/logger/logger.go

### 14. 为"减少行数"删减 task.md 详细实现步骤
- **错误**：重组 task.md 时，为减少行数删除了每个任务的详细实现步骤
- **正确做法**：宪法第1.3条明确规定 task.md 必须包含详细实现步骤，不可删减
- **违反**：宪法第1.3条"task.md中写入每一个task的详细实现步骤"
- **根本原因**：将"减少行数"的优化目标置于宪法要求之上
- **自动约束**：任何涉及 task.md 的修改，必须保留详细实现步骤和验收标准

## 代码审查要点

### 检查清单
在提交代码前，确保：
- [ ] 是否遵循"测试先行"原则？
- [ ] 是否删除了未使用的导入？
- [ ] 是否避免了不必要的抽象？
- [ ] 是否使用了简单的函数和数据结构？
- [ ] 是否使用了标准库？
- [ ] 是否正确处理了错误？
- [ ] 是否更新了 task.md 的进度？
- [ ] 配置格式是否为 YAML？

## 变更记录

### 12. 关于 Logger nil-check 模式的争议

**背景**：
- lesson.md #11 推荐使用 nil-check 模式避免空指针解引用
- 05.todo.md #5 要求简化为直接调用 `logo.Info()`

**分析**：
- nil-check 模式是防御性编程，但代码冗余
- 直接调用更简洁，但要求 logger 必须已初始化

**建议**：
- 如果 logger 在程序启动时必定初始化 → 可简化
- 如果存在 logger 未初始化的代码路径 → 保留 nil-check
- 或者使用 logo 包直接调用（不通过 wrapper）
