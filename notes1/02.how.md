## 一、架构定位

### 1.1 核心定位

PersonalClaw（PC）的定位是 **AI Agent 操作系统内核**：

```
┌─────────────────────────────────────────────────────────────┐
│                      Agent 应用层                            │
│  (唯一的 Agent：通过 config.yml 配置)                         │
└─────────────────────────────────────────────────────────────┘
                            │
┌─────────────────────────────────────────────────────────────┐
│                      插件层                                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│  │  LLM     │ │  Web     │ │ Channel  │ │  Tool    │        │
│  │ Provider │ │ Search   │ │ Plugins  │ │ Plugins  │        │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘        │
└─────────────────────────────────────────────────────────────┘
                            │
┌─────────────────────────────────────────────────────────────┐
│                      PC 核心                                │
│  (Agent 生命周期、插件系统、通信协议、权限控制、记忆系统)       │
└─────────────────────────────────────────────────────────────┘
                            │
┌─────────────────────────────────────────────────────────────┐
│                      操作系统层                              │
│  (Linux/macOS/Windows)                                       │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 与 Linux 内核的类比

| 层级 | Linux 内核 | PC 核心 |
|-----|-----------|---------|
| 核心职责 | 进程管理、内存管理、文件系统、设备驱动 | Agent 生命周期、插件系统、通信协议、权限控制 |
| 可扩展性 | 内核模块 | 插件系统 |
| 用户空间 | 应用程序、系统工具 | Agent 应用、插件 |
| 通信机制 | 系统调用 | stdio/gRPC 协议 |
| 安全机制 | 用户权限、命名空间 | 插件权限、沙箱隔离 |

## 二、插件化架构

### 2.1 设计原则

1. **核心零依赖**：核心不包含任何第三方 SDK
2. **插件独立演化**：每个插件是独立项目，独立维护
3. **跨语言支持**：插件可用任何语言实现
4. **可替换性**：插件可热插拔，不影响核心运行
5. **权限隔离**：插件声明所需权限，核心进行控制

### 2.2 插件类型

| 插件类型 | 职责 | 示例 |
|---------|------|------|
| **LLM Provider** | 对接各种大语言模型 | OpenAI、Anthropic、Ollama |
| **Web Search** | 对接各种搜索引擎 | Google、Bing、SerpAPI |
| **Channel** | 对接各种通讯渠道 | Telegram、飞书、Discord |
| **Tool** | 对接各种外部工具 | Linux 命令、Git、Docker、Jira API |

### 2.3 插件通信协议

#### stdio 协议（推荐）

```
核心进程                    插件进程
   │                          │
   │  ─────────── 请求 ──────>│
   │    {"type": "call",      │
   │     "method": "complete",│
   │     "params": {...}}     │
   │                          │
   │  <───────── 响应 ─────────│
   │    {"result": {...}}     │
   │                          │
```

**优点**：
- 跨语言支持
- 简单可靠
- 天然进程隔离

**消息格式**（JSON）：

```json
// 请求
{
  "version": "1.0",
  "id": "req-001",
  "type": "call",
  "method": "llm.complete",
  "params": {
    "model": "gpt-4",
    "messages": [...]
  }
}

// 响应
{
  "version": "1.0",
  "id": "req-001",
  "type": "response",
  "result": {
    "content": "...",
    "usage": {...}
  }
}
```

## 四、Agent 模型

### 4.1 Agent 结构

```go
type Agent struct {
    Name        string            // 名字
    Profession  string            // 职业（可选）
    Personality []string          // 性格特征（可选）
    Skills      []Skill           // 技能列表（从 skills 目录自动加载）
    Memory      *Memory           // 记忆
    State       AgentState         // 当前状态
}
```

### 4.2 配置文件结构

PC 运行时读取 `~/.pc/config.yml` 作为主配置文件：

```yaml
# ~/.pc/config.yml

# Agent 配置
agent:
  name: PersonalClaw           # Agent 名字
  profession: 通用助手         # 职业（可选）
  personality:                 # 性格特征（可选）
    - 友好
    - 专业

# System Prompt 配置
system_prompt:
  file: ~/.pc/agents.md        # system prompt 文件路径（可选，默认：~/.pc/agents.md）

# 工作目录
workspace: ~/workspace

# 其他系统配置
log_level: info
```

### 4.3 插件目录结构

插件存放在 `~/.pc/plugins/` 目录，按类型组织，自动加载：

```bash
~/.pc/plugins/
├── llm/
│   └── openai/
│       ├── plugin.yml          # 插件元信息
│       ├── config.yml          # 插件配置参数
│       └── bin/openai-llm      # 插件可执行文件
└── channel/
    └── telegram/
        ├── plugin.yml
        ├── config.yml
        └── bin/telegram-bot
```

首次启动时，自动生成两个示例插件。

### 4.4 Skills 目录结构

技能文件存放在 `~/.pc/skills/` 目录，自动加载：

```bash
~/.pc/skills/
├── code_review.md
├── project_build.md
├── deployment.md
├── data_analysis.md
└── ...
```

每个技能文件是一个 Markdown 文件，描述技能的使用方法和工具组合。

**示例：code_review.md**

```markdown
# Code Review Skill

## Description
Perform code review on given code.

## Tools Required
- git: read file content
- openai: analyze code quality

## Usage Pattern
1. Get the code to review from user
2. Read the file using git tool
3. Ask LLM to analyze the code
4. Return review comments to user
```

### 6.1 权限声明

插件必须声明所需权限：

```json
{
  "permissions": {
    "network": ["api.openai.com"],
    "filesystem": ["read:~/projects"],

  }

```

### 6.2 权限类型

| 权限类型 | 说明 | 示例 |
|---------|------|------|
| network | 网络访问 | 允许访问哪些域名 |
| filesystem | 文件系统 | 读写哪些目录 |
| system | 系统命令 | 允许执行哪些命令 |

### 6.3 沙箱隔离

- 插件运行在独立进程
- 通过协议通信，无直接内存访问
- 核心监控插件资源使用

## 十一、编码规范

### 11.1 命名规范

| 类别 | 规范 | 示例 |
|------|------|------|
| 缩略词 | 驼峰式 | `sessionId` ✓ `sessionID` ✗ |
| Receiver | 统一使用 `my` | `func (my *Engine) Process()` |
| 文件命名 | 反映主要类型名 | `skill_manager.go` → `SkillManager` |
| 时间戳 | 毫秒级 | `UpdateAt`, `CreateAt`, `Ts` |
| ID 生成 | ULID | 方便数据库自增 |

### 11.2 接口与实现分离

- 接口定义：`memory_service.go`
- 实现文件：`memory_service_impl.go`

### 11.3 日志规范

- **库**: `github.com/lixianmin/logo`
- **方法**: 优先使用 `logo.JsonI()`, `logo.JsonW()`, `logo.JsonE()`
- **禁止**: 使用 `fmt.Println` 打印日志（CLI 用户交互除外）

### 11.4 配置规范

- **格式**: YAML (`.yml`)，不使用 JSON
- **插件配置**: `~/.pc/plugins/<type>/<name>/config.yml`
- **插件参数**: 分散在各自插件目录，不在主 config.yml 中

### 11.5 Goroutine 管理规范

**强制要求**: 所有启动新 goroutine 的地方，必须使用 `github.com/lixianmin/got/loom` 包中的 `loom.Go()` 函数。

**示例代码**:

```go
import "github.com/lixianmin/got/loom"

// 错误: 直接使用 go 关键字
go my.backgroundTask()

// 正确: 使用 loom.Go()
loom.Go(func(later loom.Later) {
    my.backgroundTask()
})

**设计原则**:
- `loom.Go()` 提供统一的 goroutine 生命周期管理
- 支持 panic 恢复和优雅退出
- 可监控和限制并发数量

## 十三、Gateway 架构设计（M7）

### 13.1 为什么需要 Gateway 层

**问题**：
- 当前 `main.go` 启动后直接退出，无法保持后台运行
- 无状态模式无法支持多客户端连接
- 无法维护持久化的会话和任务调度

**解决方案**：
- 引入 Gateway 层作为常驻 daemon
- CLI 通过 RPC 与 Gateway 通信
- Gateway 管理 Engine 和插件生命周期

### 13.2 Gateway 职责

| 职责 | 说明 |
|-----|------|
| **生命周期管理** | 启动/停止 daemon，pidfile 管理 |
| **RPC 服务** | 监听 Unix Socket，处理 CLI 请求 |
| **协调器** | 管理 Engine、PluginManager、AgentManager |
| **状态持久化** | 维护会话状态、任务队列 |

### 13.3 Gateway 启动流程

```
pc gateway start
    │
    ▼
检查 pidfile ──→ 已存在? ──→ 是 → 检查进程存活 ──→ 存活 → 报错退出
    │                        │                        │
    │                        │                        ▼
    │                        │                       清理 pidfile
    │                        │                        │
    │                        ▼                        │
    │                       否                        │
    │                        │                        │
    ▼                        ▼                        ▼
初始化 Gateway ──→ 初始化 Engine、PluginManager
    │
    ▼
加载 Agent 配置
    │
    ▼
扫描并加载插件
    │
    ▼
启动 RPC Server (Unix Socket)
    │
    ▼
写入 pidfile
    │
    ▼
进入事件循环
```

### 13.4 RPC 通信协议

**传输层**: Unix Socket (`~/.pc/pc.sock`)
**协议**: JSON-RPC 简化版
**权限**: 文件权限 0600（仅当前用户）

### 13.5 TUI 架构设计

**设计目标**: TUI 作为 CLI 与 Gateway 交互的富终端界面，提供类似 Claude Code 的体验。

**TUI 功能特性** (CLI-010):
- **@命令**: 支持 `@skillname` 引用技能、`@filepath` 引用文件
- **Slash Commands**: `/quit`, `/exit` 等命令
- **代码高亮**: 代码块语法高亮显示
- **历史记录**: 命令历史保存与检索
- **自动补全**: Tab 补全技能名、命令等

**与 Channel 的关系** (CLI-011):
```
┌─────────────────────────────────────────┐
│              Gateway Daemon              │
│                                          │
│  ┌──────────────┐    ┌──────────────┐   │
│  │     TUI      │    │   Telegram   │   │
│  │   (stdio)    │    │   Channel    │   │
│  └──────┬───────┘    └──────┬───────┘   │
│         │                   │           │
│         └───────┬───────────┘           │
│                 │                       │
│          ┌──────▼──────┐                │
│          │   Engine    │                │
│          │  (Agent)    │                │
│          └─────────────┘                │
└─────────────────────────────────────────┘
```
- TUI 和 Channel 插件是独立的输入源
- 两者可同时运行，消息都路由到同一个 Agent
- TUI 走 Unix Socket RPC，Channel 插件走 stdio 协议

**状态管理**:
- TUI 不维护 Agent 状态，只负责渲染和输入
- 所有状态由 Gateway 统一管理
- TUI 可查询 Gateway 状态显示在界面上

```
Client (CLI/TUI)          Gateway (Daemon)
        │                         │
        │ ─────── connect ──────> │
        │                         │
        │ ─────── Request ──────> │
        │  {"method":"ProcessMessage",
        │   "params":{...}}       │
        │                         │
        │ <────── Response ────── │
        │   {"result":{...}}      │
        │                         │
        │ ─────── close ────────> │
```

### 13.6 System Prompt 配置设计

**设计原则** (CLI-015):
- agents.md 文件路径可通过 `config.yml` 配置
- 文件内容直接作为 system prompt 的前缀
- 无需复杂的解析逻辑，保持简单

**配置示例**:
```yaml
system_prompt:
  file: ~/.pc/agents.md        # 支持绝对路径或相对于 ~/.pc/ 的路径
```

**加载逻辑**:
1. 读取 config.yml 中的 `system_prompt.file` 配置（可选，默认 `~/.pc/agents.md`）
2. 如果文件存在，直接读取全部内容作为 system prompt 前缀
3. 如果文件不存在，使用默认 system prompt
4. 追加 skills 描述和可用工具列表形成完整 system prompt

### 13.7 Gateway Restart 设计 (CLI-014)

**职责**:
- `pc gateway restart` = `pc gateway stop` + `pc gateway start`
- 目标是让新编译的版本生效

**流程**:
```
pc gateway restart
    │
    ▼
执行 stop 逻辑
    - 读取 pidfile 获取 PID
    - 发送 SIGTERM 信号
    - 等待进程退出
    - 清理 pidfile
    │
    ▼
执行 start 逻辑
    - 检查 pidfile
    - 初始化 Gateway
    - 启动 RPC Server
    - 写入 pidfile
    │
    ▼
返回结果
```

## 十四、技术债务与改进计划

### 14.1 Session 对象抽象

**当前问题**：
- `Engine` 管理 `map[string]bool sessions`（sessionId → 是否存在）
- `Memory` 管理 `map[string][]Message sessions`（sessionId → 消息列表）
- `Memory` 管理 `map[string]int limits`（sessionId → 上下文限制）

sessionId 到具体对象的映射关系分散在两个模块中处理。

**改进方案**：
抽象出 `Session` 对象，统一在 `Engine` 中按 sessionId 管理：

```go
type Session struct {
    Id      string
    Messages []Message
    Limit   int
}

type Engine struct {
    sessions map[string]*Session  // sessionId -> Session
}
```

消息写入/读取、上下文窗口管理等逻辑都应在 `Session` 对象中实现。

### 14.2 文件命名规范

**当前问题**：
- `internal/skill/skill.go` 包含 `SkillManager` 类型

**改进方案**：
- `skill.go` 定义 `ISkillManager` 接口和 `Skill` 类型
- `skill_manager.go` 实现 `SkillManager` 结构体

遵循"文件名应反映文件中主要类型名"的规范。

### 14.3 插件协议复用

**当前问题**：
- 插件（如 `examples/plugins/llm/openai`）定义了自己的 `Request`/`Response` 结构体
- 与 `pkg/protocol/message.go` 中的定义重复
- 主项目协议变更时，插件需要被动修改

**改进方案**：
1. **本仓库插件**：直接导入 `github.com/lixianmin/pc/pkg/protocol`
2. **外部插件**：复制协议定义，保持与主项目兼容
3. **长期方案**：将协议包独立为单独模块（`pc-protocol`）供插件依赖

### 14.4 DecisionEngine 架构升级

**当前问题**：
- `NewDecisionEngine` 使用简单的关键词匹配
- 无法处理复杂语义和上下文

**改进方案**：
- 基于 Agent Loop 架构，让 LLM 决策是否需要使用工具/技能
- 将决策逻辑从本地关键词匹配迁移到 LLM 判断
- 依赖 M3-003（核心引擎消息处理）完成后实现
